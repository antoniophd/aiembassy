# 5. Build the checks

No person reviews the agents' work before it is accepted, so the checks are the quality system. Build them in
this order: code first, then a second model, and say plainly what neither can do.

## Checks by code

Code is exact and cheap. Use it for everything that can be read without judgement:

- **Citations exist.** Every point cites a segment label that exists.
- **Figures and quotations.** A number or a quotation must appear in the cited segment (or, for references such
  as a document symbol, somewhere in the record). A quotation of three words or more is verbatim.
- **Speakers.** A delegation named as speaking spoke in the cited segment. Presiding officers and the secretariat
  are not delegations.
- **Votes.** A tally is read from the chair's announcement. If it cannot be read without interpreting it, it is
  written as "unclear in the record", never guessed.
- **Group statements.** Every statement made on behalf of a group appears in the report.
- **The decision.** It names interests and red lines that exist in the profile; it keeps the option the memo
  offered; it stands with groups that actually defended the same position in that meeting.
- **The cable.** It uses only names, figures and symbols from the accepted report, keeps the decision, and stays
  within its length.
- **Language.** No internal codes, no model names, no talk of the machinery in visible text.

## Checks by a second model

Some claims need reading, not matching: "the speaker supported the text" against a segment where the support is
implicit. Send each claim of a report, with its segment, to a model of a **different family** from the writer's,
and ask only: supported, not supported, contradicted. Same-family models share blind spots.

## What happens on failure

- A document that fails is redone by its author, with the exact reasons it failed.
- If it fails again, what happens depends on whether the file can do without it:
  - **A document the file needs** (the triage, the note, the report, an opinion, the options memo, the decision,
    the statement) keeps the file open. It gets one more attempt in a later run, told every earlier rejection.
    Meanwhile the file is in preparation, never adopted. If that attempt fails too, the file is not adopted.
  - **A document the file can do without** (the cable, the press pack) is dropped, and the file goes on without
    it.
- Never accept a failed document anyway.
- Record every check result, passed or failed, next to the document.

## Repair by code, carefully

Some faults are safe to fix in code (a delegation named in a list without speaking is removed from the list).
Each repair is logged. Never let code add content; it may only remove or correct what it can prove wrong.

## Say what the checks do not cover

They show that a document is supported by its source and consistent with itself and the profile. They do not show
that the source is accurate or that the position is wise. Put that sentence where readers will see it.

## Checklist

- [ ] Every rule that can be checked by code is checked by code.
- [ ] Claims are verified by a model of another family than the writer's.
- [ ] A failed document is redone with its reasons; a second failure keeps the file open or drops the document,
      and is recorded, never accepted.
- [ ] Every check result is stored with the document.
- [ ] Code repairs only remove or correct, and each repair is logged.
- [ ] The limits of the checks are stated on every published page.
